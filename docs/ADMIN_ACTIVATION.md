# Activate 224 Live House operations

The code supports live admin independently of customer payment activation. Neon production and development databases are now provisioned with both migrations; see [Neon setup](NEON_SETUP.md). The Worker connection, first owner identity and Access MFA application still need activation.

1. Store the production pooled Neon URL for the restricted `venue_app` account as the Cloudflare Worker runtime secret `DATABASE_URL`, and set `DATABASE_DRIVER=neon`. Keep the URL out of GitHub, browser code and chat. Runtime secrets are separate from Workers Builds variables.
2. Both migrations are already applied. For future migrations, use a separate owner/migration connection in a trusted terminal with `DATABASE_DRIVER=pg`; run `npm ci`, then `npm run db:migrate`. Do not use the restricted runtime account for schema changes or run `db:demo` against the live database.
3. The first owner account has already been created after explicit user confirmation. Do not rerun the bootstrap. On a new independent environment only, set `OWNER_EMAIL` to the explicitly confirmed owner email in a trusted terminal and run `npm run db:owner` once; it does not send an invitation or change external identity-provider permissions.
4. In Cloudflare Zero Trust, create an Access application covering BOTH `/admin/*` (including `/admin`) and `/api/admin/*` on the venue hostname. Require individual identity login and MFA. For independent MFA, enable it at organization level and require it in the app and every Allow policy; a policy can override application settings. Do not use a Bypass or Service Auth policy for admin paths. Keep the public booking routes outside this application. Use short Access sessions (one hour recommended) and Require every login for MFA.
5. Copy the Access team issuer (`https://YOUR-TEAM.cloudflareaccess.com`) and the app Audience/AUD tag into Worker runtime settings `CF_ACCESS_ISSUER` and `CF_ACCESS_AUD`. Set `APP_ORIGIN` to the exact venue origin (no trailing slash). Only after reviewing the MFA policy, set `CF_ACCESS_MFA_REQUIRED=true` and `ADMIN_ENABLED=true`.
6. Open `/admin/operations` and sign in. The application verifies the signed Access JWT, expiry, audience, issuer and human identity. It then checks the active PostgreSQL account on every request. Owner/manager can operate venue records; staff can see only their assigned concierge work, without payment/customer contact details. Owners can create team records and disable accounts. Updating an existing account revokes its previous tokens until a fresh Access login. Changing the final active owner to another role or disabling it is rejected.
7. Create the space with actual prices/policies, set opening hours, and add inventory/staff shifts and services. Check two different staff accounts and an unauthorized account. Test direct Worker URL requests too: a missing or spoofed Access assertion must be denied. Confirm audit records identify the acting account.

Sign out uses `/cdn-cgi/access/logout`. Account revocation is checked in PostgreSQL, independently of the remaining Access session lifetime. Access owns login rate limits, MFA enrollment and identity recovery. The MFA marker in configuration records that the external policy was reviewed; it is not an MFA verifier by itself. Do not turn it on without that policy.

Payment operations show immutable provider state plus a separate review queue. Recording a review does not mark a payment paid or issue a refund. Production customer checkout, automatic reconciliation/refunds, receipt generation and notification delivery still require a real provider/driver implementation. Media editing accepts published HTTPS URLs and video posters; signed storage uploads remain to integrate with the owner’s storage account.

Reference: Cloudflare Access [JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) and [MFA policy configuration](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/mfa-requirements/).
